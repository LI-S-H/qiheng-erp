## 1. 知识的职责与专业依据

专家知识要回答：在什么场景下，需要权衡哪些方面；哪些数据足以支撑判断；采用什么计算方法；哪些结论在证据不足时不能给出。

- 项目业务事实：以实际 Java 实现为准，表设计用于补充字段说明；有分歧时注明，不把旧知识文件中的描述直接作为事实。
- 通用方法：参考供应链教材、专业组织和产品官方资料，按本 ERP 的数据条件改写。专业公式的适用假设也是知识的一部分。
- 企业政策：预算、交付期限、可接受缺货风险、利润底线等，由用户或受维护的企业配置提供，模型不自行发明。
- 场景推演：允许采用明确列出的假设，但输出必须标注“情景测算”，不得称为已查到的事实或已经实现的效果。

结构借鉴 Skill 的“适用条件—输入—处理步骤—结果—边界”，不照抄通用 Skill 中的默认参数、工具权限或未经核实的业务规则。

## 2. 当前 ERP 的能力与证据地图

“可计算”表示已有字段可形成证据；未来执行时仍需通过授权 Schema、样本和质量检查。当前图拓扑尚未接完取数、方案与报告链路，不把模型公式写成已经运行的功能。

| 场景 | 当前可用数据 | 当前能够支持 | 需要补充或明确的边界 |
|---|---|---|---|
| 当前库存与安全线 | `warehouse_stock.stock_qty/locked_qty`；`product.safety_stock_qty/quantity_precision` | 按仓库、产品判断账面可用量与安全线差额 | 安全库存配置是产品级；库存余额没有合格/不合格品分桶 |
| 日常或紧急补货 | 上述库存、采购剩余量及预计到货日、销售确认出库历史、未履约销售 | 计算安全线缺口；在给定需求和时间窗口下测算补货量 | 未来需求需模型或用户参数；须处理预测与已锁订单的重叠，不能保证未来到货 |
| 采购与供应商选择 | `supplier_product` 的报价、有效期、MOQ、评分、历史平均交期，供应商及产品状态 | 候选筛选、报价金额、评分比较、起订量影响 | MOQ/有效报价是建议采用的方案约束，并非当前下单接口都强制检查；供应商实时产能未知 |
| 跨仓调拨 | 各仓当前库存、销售出库历史、产品单位精度 | 估计调出余量、比较对调出仓的影响 | 没有独立调拨单、运输时效和费用模型；库存调整单不能证明一次调拨业务已完整执行 |
| 积压去化 | 当前库存、销售出库时间序列、参考价/报价 | 低周转候选、静态覆盖天数、不同去化手段比较 | 无批次库存年龄、到期日、仓储费；不得宣称“这批库存已存放多少天” |
| 促销与调价 | 销售价格与数量历史、当前库存、参考价/报价 | 选品筛查；给定价格、成本、费用和销量假设后做贡献测算 | 无完整促销活动标签、实验对照、实际销货成本及活动费用账；不能自动识别促销因果效果 |
| 供应异常 | 采购预计到货日、剩余量、确认入库与质检事实、评分 | 查逾期未收、分析对补货的影响、比较替代候选 | 催交承诺、未来产能、替代品兼容性通常需外部确认 |
| 订单履约 | 销售明细、预计发货日、锁定与累计出库量 | 识别未履约量、分批处理情况、潜在延误 | 无客户优先级规则时不能自行决定牺牲哪个订单；预计发货日不是客户实际收货日 |
| 退货与质量 | 退货来源、审核与处理量、可用库存、入出库质检记录 | 可退量、库存方向与供应影响 | 退货流程有数据不代表售后费用、退款、质量隔离和重新上架均有闭环 |
| 安全库存策略 | 已配安全库存、日出库序列、历史采购周期 | 进行候选策略评估、比较参数情景 | 需明确服务目标、统计假设、样本代表性；不得直接覆盖产品配置 |

企业未提供的运费、持有成本、订单固定成本、毛利底线、促销提升率、批次保质期等，不以行业默认值代替实际事实。

## 4. 单条知识的固定结构

每条知识应有稳定编号，便于审核问题指向具体规则；编号不是新的接口字段。

| 栏目 | 应写什么 |
|---|---|
| 知识编号与业务问题 | 例如 `REP-001`：给定保护期，还需补充多少供应 |
| 适用条件 | 什么目标、粒度和时间范围下适用 |
| 不适用条件 | 哪些情形必须换模型或降低结论强度 |
| 必需证据 | 业务含义、来源字段、粒度、单位、状态、时间口径 |
| 参数来源 | 哪些来自 ERP，哪些来自用户，哪些需要拟合或估计 |
| 公式与步骤 | 变量定义、计算顺序、取整与边界、依赖关系 |
| 方案取舍 | 用什么条件比较不同动作，不预先固定胜出方案 |
| 缺数处理 | 能继续回答什么、必须保留什么不确定性 |
| 审核检查点 | 只检查本场景必需项；写清问题发生在哪类证据上 |
| 结果表达与来源 | 区分事实、估计、假设；关联计算产物与专业资料 |

示例标题采用 `## REP-001 补货数量与到货时点`，其下用三级标题或加粗标签。每个二级标题自带场景名称，避免现有加载器去掉文件一级标题并合并文件后丢失上下文。

## 5. 所有计算共用的数值规则

### 5.1 先统一量纲

以下公式默认使用真实业务数量、元、自然日；营业日口径需另有日历参数，不混用。

```text
业务数量 q = 数据库数量 Q100 / 100
业务单价 p = 数据库单价 Pcent / 100
业务金额 a = 数据库金额 Acent / 100

q × p 的结果单位：元
直接使用数据库整数时：金额（分）= Q100 × Pcent / 100，再按金额规则舍入
同口径数量相减仍是数量；数量相除通常是比例；两个放大数相乘不能仍按 ×100 解读
```

例如数量 `2500` 代表 25 件，单价 `3520` 代表 35.20 元，金额是 880.00 元，即 `88000` 分。`product.reference_purchase_price/reference_sale_price` 本来就是元，不能再除以 100。

数量、金额与比值运算使用 Decimal 或等效精确计算；库内大整数相乘要防溢出。实际创建业务单据仍调用业务 Service 的校验与舍入规则，不把知识公式作为第二套写入实现。

同单位标签也不代表不同产品能相互替代。供需、缺口与调拨必须匹配同一产品及单位；不同产品可以汇总金额或记录数，不把它们的数量合计解释成可互换的供应。

### 5.2 四种方法属性

| 属性 | 含义 | 允许怎样表达 |
|---|---|---|
| ERP 确定口径 | 由现有字段与状态确定 | “截至某时点，账面可用量为……” |
| 参数化情景 | 公式可算，但关键值由用户或假设给定 | “按交期 L、目标 S 的假设测算……” |
| 待验证统计模型 | 需要样本、拟合与样本外验证 | “使用方法 M，回测误差为……，预测为……” |
| 当前条件不足 | 缺关键事实或模型假设不成立 | “现有数据只能支持……，尚不能确定……” |

数据不足本身不是数学上的“方案不可行”。知识只要求说明缺口；图状态由既定节点按协议判定，不由文档或模型任意改写。

## 6. 计算方法目录

### 6.1 当前字段可以支持的确定计算

| 编号 | 公式或方法 | 数据与口径 | 使用边界 |
|---|---|---|---|
| F01 | `A = H - R` | H 为当前库存，R 为仓储锁定库存；同仓同产品同一快照 | A 是账面未预占量，不保证都是合格可售品；负数是异常线索，不静默裁成零 |
| F02 | `I_all = Σ(q_order - q_received)` | 采购状态为 APPROVED/PARTIAL_INBOUND，按采购明细唯一计数 | 负剩余量先标数据异常；不叠加待确认入库单，不把所有在途都当当前可用 |
| F03 | `d̄ = Σx_t / N` | x_t 为日销售确认出库数量；补齐已知完整日历中的零出库日 | 是历史出库速度，不等于全部真实需求；缺失数据不补成零 |
| F04 | `DOC = A / d̄` | 静态覆盖天数；A≥0、d̄>0且粒度一致 | 忽略未来到货和需求变化；d̄=0时显示不可估计，不报“永不缺货” |
| F05 | `S_rec = 0.3S_price + 0.3S_delivery + 0.3S_quality + 0.1S_service` | 现有供应商评分实现；各分值先还原至0—100 | 任一必要分项为空则综合不可用，不当零分、不重新分配权重；高分不是交付保证 |
| F06 | `Age_no_sale = 业务日 - 最近销售确认出库日` | 以 SALES_OUT 事实识别无销售出库间隔 | 不是当前库存批次年龄；无历史时为未知，不能推成无限积压 |

F03 的稳定日均值可作初始预测基线，但“能从历史算出均值”与“适合预测未来”是两项检查。

现有评分的分项也应保留业务定义：价格分为 `min(100, 参考采购价/有效报价×100)`，两种价格先统一为元；质量分为 `合格金额/(合格金额+不合格金额)×100`，不是简单件数合格率；交付分为 `clip(100×(1-逾期折算罚额/到期应交金额),0,100)`。金额分母为零或必要样本缺失时不算有效分。其样本窗口、逾期系数与舍入继续采用评分服务，不在专家知识中另定一套。

### 6.2 需要政策或场景参数的计算

| 编号 | 公式或方法 | 必须明确的参数与限制 |
|---|---|---|
| F07 | `Q_base = max(0, D_new,h + S_end - A - I_h)` | D_new,h只含未被当前预占覆盖、且未重复计入的未来需求；S_end是期末缓冲目标，I_h按时间可达；还需逐日平衡 |
| F08 | `T_out = max(0, A_donor + I_donor,h - D_new,donor,h - S_donor,end)` | 调出仓需保留自身需求与缓冲；这是保护期总量上限估计，不是“现在可发”的许可；还要按实际调出时点核验 |
| F09 | `Q_order = 0 (Q_base=0)；否则 ceil(max(Q_base,MOQ)/u) × u`，`u=10^(-precision)` | MOQ作为已确认的本次采购条件；数量精度来自新建产品/历史单据快照；包装倍数另需提供，不能拿MOQ当倍数 |
| F10 | `采购货值 = Σ(Q_order,i × p_i)` | 有效且经确认的价格；只表示货值，不自动含运费、税费、资金及仓储成本 |
| F11 | `ΔC = q1×m1 - q0×m0 - F`；`m_j=p_j-c_j-v_j` | 对比同一活动期间的正常情形与活动情形；成本、变动费、新增活动费、销量均需有来源；这是增量贡献情景，非净利润 |

F07、F08 是按本项目的“已扣锁定”口径编写的供需平衡关系，不是现有业务接口已经实施的补货/调拨策略。到货时点影响可用量，期末总量足够不代表中途不会断供。[Microsoft 按时间处理供需与重订货策略](https://learn.microsoft.com/en-us/dynamics365/business-central/design-details-handling-reordering-policies)

### 6.3 有模型依据，但需要验证后才能采用

| 编号 | 模型与公式 | 适用与启用条件 | 当前缺口或限制 |
|---|---|---|---|
| F12 | 简单指数平滑：`ℓ_t=αx_t+(1-α)ℓ_(t-1)`，`x̂_(t+h)=ℓ_t` | 0≤α≤1，初值与α要记录；用于无明显趋势和季节结构的序列 | 需要充分历史、异常检查和回测；不能统一默认α=0.3 |
| F13 | 固定交期安全库存：`SS=z×σ_d×√L`；重订货点 `ROP=μ_d×L+SS` | 固定L、日需求近似独立同分布，交期需求近似正态；z由目标周期服务水平确定 | 历史出库可能受缺货截尾；L是规划交期参数，历史平均交期不能证明固定L；不自动改现有安全库存 |
| F14 | EOQ：`Q*=√(2DK/h)` | D为年需求，K为每次订货相关固定成本，h为每单位每年持有成本；经典模型假设稳定需求、单次到齐等 | 当前无完整K、h；不能只用采购单价自动算EOQ，不能给“最优采购量”保证 |

财务口径的库存周转率通常还需要匹配期间的销货成本和平均存货价值；当前数据不足以直接形成这套口径。`出库量/当前库存`可作为另行定义的运营比值，不能贴上标准财务周转率的名称。

指数平滑的假设与选型参考 [Forecasting: Principles and Practice，第8章](https://otexts.com/fpp3/exponential-smoothing.html)。验证采用按时间滚动的样本外预测，比较相同产品、相同预测长度的 MAE 或 RMSE：`MAE=mean(|y-ŷ|)`、`RMSE=√mean((y-ŷ)²)`。不随机打乱时间；零销量较多时不使用以实际值作分母的 MAPE。[预测误差与时间交叉验证，第5章](https://otexts.com/fpp3/toolbox.html)

安全库存的统计假设及周期服务水平参考 [Peter L. King，Understanding safety stock，APICS 文章（MIT 托管）](https://web.mit.edu/2.810/www/files/readings/King_SafetyStock.pdf)。周期服务水平不是按数量计算的需求满足率，不可把95%的周期服务目标称为保证满足95%的需求量。交期明显波动、促销或间歇需求不直接套固定L公式；周期复核时应另建覆盖L+复核间隔的策略。[NC State 服务水平说明](https://scm.ncsu.edu/scm-articles/article/reorder-point-formula-inventory-management-models-a-tutorial)

EOQ 的参数与假设参考 [MIT OCW，Deterministic-demand Inventory Models，第20—27页](https://ocw.mit.edu/courses/15-772j-d-lab-supply-chains-fall-2014/b0b41cc09a83ffa4cf1335ac65f5f9ab_MIT15_772JF14_Lec13.pdf)。ROP解决触发时点，EOQ讨论批量；二者不能互相替代。[Oracle 库存规划与补货](https://docs.oracle.com/cd/E26401_01/doc.122/e48820/T291651T292324.htm)

## 7. 样稿一：REP-001 补货数量与到货时点

### 7.1 适用条件

目标是评估一个仓库某产品在未来保护期内是否需要新增供应。保护期、补货目的和期末目标必须明确。仅检查当前是否低于安全线时，只需库存与安全线；不强制引入完整预测模型。

### 7.2 必需证据与来源

| 变量 | 来源 | 粒度、单位和约束 |
|---|---|---|
| H、R、A | `warehouse_stock.stock_qty/locked_qty` | 仓库×产品；数量×100还原；记录统一asOf；本表没有deleted字段 |
| S配置、precision | `product.safety_stock_qty/quantity_precision` | S是产品级配置；用作本仓分析参考时说明适用政策，不把它称为已独立配置的仓级策略 |
| x_t | `stock_bill`关联`stock_bill_item`的 SALES_OUT、`confirmed_at`、`change_qty` | 按实际确认日、仓库×产品汇总，销售出库取负变动的相反数；不用审批金额统计替代 |
| C_h | `sales_order`关联`quantity/outbound_qty`及预计发货日，并核对仓储预占 | 识别保护期内已预占、尚未出库且被预测覆盖的销售需求；不能直接使用历史明细locked_qty当剩余量 |
| I候选 | `purchase_order`关联`purchase_order_item.quantity/inbound_qty` | 同仓同产品；APPROVED/PARTIAL_INBOUND；预计到货日和剩余量；历史变更或缺失需要核对 |
| MOQ、p | `supplier_product.min_order_qty/quoted_purchase_price/quote_valid_until` | 供货关系、供应商与产品适用；报价需在采用时有效；实际合同/供应商确认可覆盖为有来源的参数 |
| h、S_end、L | 用户目标、受维护政策或明确建模方案 | h是保护期，S_end是期末目标，L是本次规划交期；均不得由模型暗中填写 |

历史单据按当时事实及明细快照解释；当前对象是否可用于新方案单独检查启用与删除状态。不能简单通过今天产品停用与否删除历史需求样本。自然日窗口采用上海业务时区和左闭右开边界。

销售实际出库量、销售审批量、净退货后销量是不同指标。销售退货单独形成一条入库/退货序列；不能把调整出入库、采购退货混成市场需求。若采用净销量，需说明退货跨期及原因，并与库存回补口径保持一致。

### 7.3 先处理需求与预占的重叠

本项目在销售提交时锁库，A已经扣除了该部分；采购退货和手工调整也可能占用R。

```text
若预测是保护期内的总销售需求 F_h：
  先识别与其同产品、同仓、同时间窗口重叠的已预占销售需求 C_h
  在明确采用“订单消耗预测”的政策时：D_new,h = max(0, F_h - C_h)

若输入已经是扣除已覆盖订单后的新增需求：
  D_new,h = 该新增需求，不再减 C_h
```

未预占的意向/草稿订单不自动成为确定需求；用户要求纳入时，先确认它是否已被预测覆盖，只加入尚未覆盖的部分。无法对齐预测与订单时，分别给出不同口径的情景，不假装已去重。

不允许计算 `总预测需求 + 全部未履约订单 - A - 在途`：它可能同时重复计入预测中的订单，又重复扣掉A已经预留的量。

### 7.4 按时间核对在途与新增供应

1. 在途按采购明细唯一计数，不再叠加入库工作单的计划量。
2. 预计到货日过期、为空或已有失约信号的剩余采购单独列为不确定供应；没有重新确认时，保守情景不将其当作确定可达量，也不直接取消原采购单。
3. 当前时点之前尚未收货的逾期单仍是未完成采购事实；“不计入可靠到货”不等于它不存在。
   此处“在途”仅指业务上已审核未收货的采购敞口，系统没有物流发运状态，不能据此说货已离开供应商或在运输途中。
4. I_h包含从当前时点到保护期末可达的供应；分析未来某月时，也要衔接当前至月初的消耗和到货，不能丢掉月初之前会到的供应。
5. 逐日或按需求关键时点计算：`PAB_free(t)=A+ΣI(≤t)-ΣD_new(≤t)`。在途在其到货时点才增加余额；同日的先后顺序未知时，对紧急需求采用保守假设或取得确认。

总量模型采用F07；新增采购/调拨必须安排在首次缺口前到达。若按现有交期赶不上，即使Q_base正确，也不能称原方案已解决紧急缺货。

### 7.5 假设案例：演示去重和起订量

以下数值全部为教学假设，不来自实际数据库。

```text
H=100件，R=30件，A=70件；保护期14天；期末目标S_end=20件
总需求预测F_h=140件，其中已被预占覆盖的销售需求C_h=30件
已确认可在期内、需求之前到达的采购剩余量I_h=40件

D_new,h = 140 - 30 = 110件
Q_base = max(0, 110 + 20 - 70 - 40) = 20件

供应商确认本次MOQ=25件，数量精度0：Q_order=25件
多补5件，应说明起订量造成的期末余量变化
报价35.20元/件：采购货值=25×35.20=880.00元
```

未消除预测内已预占订单的重叠会算成50件，重复补了30件。25件只是满足该情景与起订量的候选批量，尚不包含运输费用，也不是EOQ最优解。

### 7.6 方案输出与派生需求

先比较可按时执行的候选：等待已确认在途、内部调拨、外部采购或组合。每种方案需列出到货时点、数量、已知货值、待确认条件、对其他仓的影响。不得默认调拨免费或最快，也不能在资料不足时宣称某供应商一定能交付。

用户选择后，方案子图应围绕所选方案产生D段分析需求。下表只示范证据规划，不引入新协议；可行性阶段已有合格数据应按实际引用契约复用，避免重复取数。

| 示例证据项 | 来源类型 | 要解决的问题 |
|---|---|---|
| D1-E1 当前库存、预占、目标与精度 | SQL | 当前能用于新增需求的量和数量粒度 |
| D1-E2 销售出库序列与未履约订单 | SQL | 形成同粒度的需求输入，并识别已预占部分 |
| D1-E3 未完成采购及到货时间 | SQL | 可达与不确定供应分别是多少 |
| D1-E4 本期新增需求与供需平衡 | PYTHON | 按选定模型去重、逐时点检验，依赖E1/E2/E3 |
| D1-E5 所选供货关系与本次价格条件 | SQL | 所选采购方案的报价、起订量和样本依据 |
| D1-E6 调整后批量、货值与余量 | PYTHON | 应用数量精度/MOQ，复核预算与到货后余量，依赖E4/E5 |

实际instruction使用业务口径并写明真实证据id，depends显式匹配；不让专家知识生成未经授权的SQL。所选方案含调拨时，还需调出仓的对应证据；纯采购方案不强制查调出仓。

### 7.7 审核检查点与缺数处理

- 必查：目标时间、仓品粒度、A的定义、预测与预占去重、可达到货时间、起订/精度、调整后的金额和期末余额是否闭合。
- 已采用未来缺货结论而未提供需求、采用采购抵扣而未提供到货时点，属于会改变结论的缺项。
- 仅问当前安全线差额时，不因缺预测、运输费用或EOQ参数而反复退回。
- 只有历史出库与当前库存时，可以报告历史速度和当前安全线差额；不能给未经说明的确定未来缺口。
- 缺供应商承诺时，可以给历史交期情景及风险；缺货运时效时，不把调拨方案判成已验证可行。
- 存在质检异常时，说明A没有隔离不合格库存；现有记录不足以还原当前坏品余额时，需人工确认可用实物，不能直接减去历史全部不合格入库量。

## 8. 样稿二：PRM-001 促销价格与增量贡献

### 8.1 适用条件与目标

用户希望比较给定活动价格、费用与销量情景的经济效果。先明确目标是增量贡献、库存去化还是收入增长，目标不同不能共用一个“成功”判据。

当前可筛查库存与历史销售；促销因果预测、会计毛利和活动自动执行不在现有完整能力内。本条适合参数化情景比较。

### 8.2 数据与参数

| 输入 | 当前来源与使用限制 |
|---|---|
| 当前库存与历史出库 | 与REP-001一致；需考虑已锁库存及活动期间补货，不把不可用存货全部投入活动 |
| 历史成交价 | 订单明细unit_price/quantity及销售时点；客户、仓库和商品组合需可比；不将参考售价当真实成交价 |
| 正常情形销量q0 | 同期间无活动时的基线估计；历史销量需校正季节、缺货和趋势，不能直接视为已知反事实 |
| 活动价格p1、销量q1 | 用户提供或经验证模型估计；记录来源，未知时计算多个显式情景，不默认销量必然提高 |
| 单位商品成本c0/c1、变动费v0/v1 | 当前无完整销货成本与活动费用账；用户可提供经确认的分析成本。报价/参考采购价仅可作明确标注的代理情景 |
| 新增固定活动费F | 用户提供或外部核实；缺失时不能默认为0并输出实际利润结论 |

所有价格与成本需采用可比的税费口径。费用不全时结论只能是已列项目下的贡献情景；不能称净利润、真实毛利或已经发生的促销收益。

### 8.3 公式与判断

单位贡献的定义参考 [OpenStax，贡献毛益](https://openstax.org/books/principles-managerial-accounting/pages/3-1-explain-contribution-margin-and-calculate-contribution-margin-per-unit-contribution-margin-ratio-and-total-contribution-margin)；固定/变动费用的线性与相关范围假设参考 [OpenStax，盈亏平衡分析](https://openstax.org/books/principles-managerial-accounting/pages/3-2-calculate-a-break-even-point-in-units-and-dollars)。以下是据此为活动比较推导的情景公式，并非本ERP现有利润计算规则。

```text
m0 = p0 - c0 - v0                     正常情形单位贡献
m1 = p1 - c1 - v1                     活动情形单位贡献
ΔC = q1×m1 - q0×m0 - F                相对正常情形的增量贡献

在m1>0、q0×m0+F>0的常规比较下：
q1_BE = (q0×m0 + F) / m1              达到正常情形贡献所需的活动销量
提升率要求 = q1_BE / q0 - 1           仅在q0>0时计算
```

这不是仅覆盖活动费的 `F/m1`；活动还必须弥补正常销量因降价减少的贡献。实际所需销量按数量精度向上取整。若m1≤0，不直接套除法；在基准贡献非负且活动费非负、目标为正时，增加销量无法达到该比较目标。

### 8.4 假设案例

以下参数全部为教学假设，并假设活动期间可以供应足够的合格商品、单位费用在该销量范围内不变。

```text
正常价p0=100元，活动价p1=90元
c0=c1=60元/件，v0=v1=5元/件
正常情形销量q0=100件，新增活动费F=200元

m0=35元/件，m1=25元/件
q1_BE=(100×35+200)/25=148件
至少需要比正常情形多卖48%，才达到原有贡献水平

若“活动卖150件”只是用户假设：
ΔC=150×25-100×35-200=50元
```

允许输出：“在以上成本、费用及150件销量假设下，增量贡献为50元。”不能输出：“降价10%必然带来50%的销量增长、增加50元实际利润。”

若可供活动的量仅120件，148件的目标在该供应假设下无法完成；需要调整价格、费用、供应或活动目标。净增量还应考虑活动前后囤货及其他商品销量被替代的影响，现有数据不足以识别时列为未覆盖影响，不随意填比例。

### 8.5 审核检查点

- 必查：活动目标、同期间正常基线、活动价格、成本代理或确认成本、费用、销量假设、库存承接、结果称谓。
- 只给降价后的销售收入，没有正常情形贡献对照，不能支持“活动更划算”。
- 只凭两期价格与销量变化，不能认定价格弹性或促销因果；样本混有不同客户、缺货和季节时需降级。
- 用户只要活动选品清单时，不强制完成盈亏模型；一旦声称利润改善，成本与费用就是必要证据。
- 低贡献促销若服务于已确认的去化目标，可继续比较损失、库存占用和替代手段，不由审核员擅自把“必须增利”设为企业政策。

## 9. 编写前已发现的口径风险

以下记录用于后续正式编写时复核，本轮不修改已有业务知识或Java实现。

1. `knowledge/shared.md` 将“数量相乘、相除仍为×100”一概而论，量纲不成立；正式条目按第5节处理。
2. `knowledge/purchase.md` 的简单净缺口公式没有展开预测消耗与锁定重叠；不能无条件作为未来补货策略。
3. 仓储表设计中部分锁库描述与实际提交时锁库存在历史差异，以销售submit代码为准。
4. 产品文档、业务知识可能把安全库存的“配置层级”与“分析粒度”混写；目前为产品级配置，仓品比较和仓级策略优化需分清。
5. `avg_delivery_days` 同时存在供应商与供货关系级，且为历史金额加权统计。当前在完全收货回写时更新；没有新样本时可能保留旧值，不保证每个查询日都已重新滚动窗口。
6. 入库按current_qty全量进入库存，质检仅记录合格/不合格量，没有对应的库存质量隔离余额。不能由历史次品量直接推出当前不可售量。

## 10. 接入与验收方式

- 当前 `ProposalPlaybook` 按文件名读取 `proposal/*.md`，构造时加载；去掉一级标题及部分说明行，不是Markdown渲染器，也不是热更新服务。
- 现有加载器把全部非占位内容交给`need_review`，不会按权限筛选专家知识。知识中的方法不能被理解为拥有额外取数权限；取数始终以授权Schema为准。
- 当前审阅提示在知识非空时会附加整份内容，因此每条规则必须自带适用条件；不能让普通DATA需求也被迫满足促销或调拨的全部维度。
- 后续方案子图按“通用+场景/动作”选择内容的能力需实际接线；不能仅新增八个文件就宣称已实现按需检索。
- 不把README、长篇编写说明或来源索引直接放进`proposal/*.md`，因为同样会被读取。运行时知识改动后需要重建/重新加载class path并重建实例；打包部署通常需重新构建、重启。
- 正式填入后，`ProposalPlaybookTest.placeholderOnlyFilesAreEmpty` 的“目录内容为空”预期需要更新；其他清洗与注入边界测试应保留。不要为通过旧测试保留空知识。
- 验收至少包括：适用场景命中、无关规则不误报、缺数据不伪造、公式和量纲可复算、重叠需求不双算、时点不足不报已解决、错误能定位到具体证据项，以及知识注入长度可控。
