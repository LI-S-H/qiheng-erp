ERP Agent 修订架构 v3：需求驱动的轮次式 ReAct

Planner 只做需求拆解；真正的 plan 节点每次只回答「当前需求完成了吗？没完成就给下一步」， 执行后回到 plan 再问一次，直到所有需求进入终态。
指导思想：凡是能由代码判定的，绝不让模型回忆。

图一 · 主循环

主干从上往下，最左侧那条回边是循环本体。evidence_commit 写完证据链就回到 plan 重新判断， 直到选不出未完成的需求才退出到 reporter。
右侧粉色是人工暂停点：plan_dispatch 产出候选骨架后先暂停给用户过目—— 此时信息已充分（用户知道缺口多少），但填充的大钱还没花，纠偏最便宜； 且用户知道系统查不到的事（如"华南仓下个月检修"）。

图二 · 输出层（reporter 之后）

关键是 reflection 的四分类：只有「真的缺数据」才回主循环补，其余各自走最省的路。

节点职责速查

节点职责关键约束
planner只做需求拆解上限 3 个需求；拆不出来可请求澄清
need_check格式、无环、依赖完备条件表达式必须可解析
plan判断当前需求是否完成 + 生成下一步一次调用；不产出任何数字
plan_dispatch更新需求状态、骨架落盘、路由纯代码，路由可单测
proposal_human候选骨架确认（人工暂停点）确认 / 调整 / 取消，调整是一等公民
task_check步骤校验同轮步骤必须互不依赖
python_task沙箱计算所有数值的唯一产出者
solution_reference查手段、适用条件、历史采用率产出 REFERENCE，不进报告数据源
evidence_commit写证据链同名 key 覆盖；总量上限 20
reporter组装叙述不新增方案、不新增数字
reflection四分类核对只有缺数据才回 plan 补
fact_check数字溯源代码先查，语义问题再上模型

硬约束：max-needs=3、max-rounds=8、max-round-steps=3、max-proposals=3、 max-report-revisions=2、max-evidence-items=20；每轮必须产生新证据，否则停止。
最容易被破坏的三条：让模型自己算数、让 plan 一轮排有依赖的步骤、让 reporter 顺手"完善"方案。
