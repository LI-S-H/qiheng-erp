# 前端页面设计思路

> 本文只保留前端架构、目录组织、权限登录态、基础框架与工作台这些**结构性设计**。
> 视觉与交互细节见 [前端开发规范](frontend-development-guide.md) 与 [前端界面风格规范](frontend-style-guide.md)；字段与接口契约见 [erp-openapi.yaml](api/erp-openapi.yaml)；页面数据来源见 `docs/database/` 下各模块库表设计。
> 各业务页面的逐页设计稿已移除：页面早已实现并多轮改版，其字段与交互由上述契约和实际代码承载，保留旧稿会与现行实现冲突。

## 1. 前端架构选择

前端软件名为 **启衡 ERP**。

前端采用 `Vue 3 + TypeScript + Vite + shadcn-vue + Tailwind CSS + Pinia + Vue Router + Axios`。

选择这套技术栈的原因：

- 项目是企业内部 ERP 管理系统，核心页面以表格、筛选、表单、弹窗、状态流转和操作确认为主；shadcn-vue 提供可控的无样式基础组件，便于统一视觉并避免组件库默认样式侵入业务页面
- Tailwind CSS 负责布局和局部样式，颜色、字体、圆角和间距通过全局 token 与共享页面类统一，不在各模块重复维护大段局部 CSS
- Vue 3 + TypeScript 能保证开发效率，同时让接口字段、登录态和业务 DTO 有明确类型约束
- Vite 启动和构建速度快，适合按模块逐步生成、逐步审核的开发节奏
- Pinia 用于保存登录态、当前用户和后续模块级缓存，状态结构清晰
- Axios 统一处理 `satoken` 请求头、响应错误和登录失效跳转，避免每个模块重复处理鉴权逻辑

## 2. 目录组织思路

前端工程放在 `erp-web` 目录下，按“基础能力 + 业务模块”组织：

```text
erp-web/
├── src
│   ├── api                 Axios 实例和统一请求函数
│   ├── layouts             后台主布局
│   ├── router              路由和登录守卫
│   ├── shared              通用类型、常量、组件和工具
│   ├── modules             按业务域拆分页面、接口和状态
│   └── styles              全局样式
└── package.json
```

这样设计的好处是每个模块可以独立审核：页面、接口封装、类型定义和局部状态都放在自己的模块目录下；公共能力只沉淀到 `shared` 和 `api`，避免模块之间互相引用过深。

## 3. 整体页面风格

启衡 ERP 面向企业内部采购、销售、仓储、管理人员和系统管理员，页面风格以“稳定、清晰、可长时间使用”为主。具体色板、字号、控件高度、表格列宽和分页行为以 [前端界面风格规范](frontend-style-guide.md) 为准，本文只保留不随模块变化的设计原则。

设计原则：

- 后台主布局采用左侧菜单 + 顶部用户区 + 主内容区，符合 ERP 用户的日常操作习惯
- 左侧导航和顶部状态栏使用同一组中性 token，内容区使用低对比浅灰背景，避免出现两个互不相关的视觉系统；已迁移的浅色应用壳路由与未迁移路由的主题切换规则由风格规范给出
- 全站使用中文系统字体栈，不依赖远程字体；页面业务正文、输入、下拉和表格主文字复用 shadcn `text-sm` 的 `14px` 基准，按钮文字统一为 `13px` 常规字重，避免操作文字压过数据内容
- 列表页的四项概览合并为单条摘要栏，筛选区和表格各保留一个容器，减少卡片堆叠和页面碎片感
- 页面优先使用列表页、筛选区、表单弹窗、详情抽屉、状态标签和确认弹窗，服务高频业务处理
- 中等宽度下筛选区自动切换为规整两列；筛选下拉使用 shadcn `Popover + Command` 组合并固定从触发框下方等宽展开；输入焦点仅显示柔和模糊辉光
- 分页底栏保持 `52px` 轻量尺寸。需要精确页码的页面可展示总数和总页数；仓库、库存余额等无总数分页页面只展示本页条数、每页条数、上一页、当前页和下一页，不要求后端额外统计总记录数
- 页面跳转保留短时加载遮罩与淡入反馈，侧栏子菜单使用基于内容高度的折叠动画，避免固定最大高度造成布局卡顿
- 所有弹窗受视口最大高度约束，长表单和权限列表必须支持纵向滚动，不能截断底部操作区
- 表格工具栏复用 shadcn `Button` 与 `Tooltip`，可操作按钮悬停时加深背景或边框，禁用批量操作提示需要先选择数据
- 所有 shadcn 文字按钮统一使用 `13px` 常规字重，行内操作、工具栏和弹窗按钮仅通过组件变体与尺寸区分操作层级
- 行内操作颜色按语义统一：详情使用青色强调，编辑使用默认文字色，启用/提交/确认等正向动作使用主色或绿色，停用使用琥珀色，取消/删除使用危险色；采购和仓库模块不得出现整组操作按钮全黑或额外图标混用。
- 新增和编辑表单提交前统一执行 `trim`、必填、长度、格式与数组非空校验；账号、角色编码等唯一字段冲突回填到对应字段，不只显示全局提示
- 查询操作使用短防抖并忽略过期响应，保存、确认、重置密码等异步动作在处理中禁用触发按钮，避免重复请求
- 视觉上避免营销页式大面积装饰，重点突出信息密度、可读性和操作确定性
- 菜单先固定展示，权限以后端接口校验为准，符合 MVP 阶段“页面入口统一展示、进入页面或查询时校验权限码”的数据库设计
- 前端不展示接口文档入口，接口文档只维护在 `docs/api/erp-openapi.yaml`，用于导入 Apifox

### 3.1 业务主数据选项治理标记

当前系统模块的角色、部门、权限码等选项属于小规模配置数据，暂时继续使用 options 接口，不纳入本轮大数据选项改造。产品、客户、供应商、供货关系和业务单据中使用的仓库选择可能随业务增长变大，不能固定取前 100 条作为全量下拉数据。

本轮审计标记如下：

| 状态 | 模块/页面 | 当前实现问题 | 后续处理方法 |
|---|---|---|---|
| 暂不改 | 系统模块 `/system/users`、`/system/roles`、`/system/depts`、`/system/permissions` | 角色、部门、权限码选项数据规模小，当前 options 接口可接受 | 保持现状；未来数据规模增长再改为分页选择 |
| 已改 | 采购供货产品 `/purchase/supplier-products` | 已取消表单全量供应商选项和启用产品前 100 条选项 | 表单供应商、产品均使用动态搜索下拉，按编码或名称请求后端第一页，默认 `pageSize=10`，并缓存已选快照用于回显 |
| 已改 | 采购订单 `/purchase/orders` | 已取消表单全量供应商、启用仓库前 100 条、启用产品前 100 条以及全量启用供货关系预加载 | 供应商、仓库使用动态搜索下拉；采购明细产品按当前供应商分页查询 `supplier_product`，默认 `pageSize=10`，不再预加载全量供货关系 |
| 已改 | 销售订单 `/sales/orders` | 已取消表单全量客户、启用仓库前 100 条、启用产品前 100 条选项 | 客户、仓库、产品均使用动态搜索下拉，按编码或名称请求后端第一页，默认 `pageSize=10`，并缓存订单快照用于编辑回显 |
| 已改 | 库存入库/出库单 `/warehouse/inbound-bills`、`/warehouse/outbound-bills` | 已取消手工补录/调整表单启用产品前 100 条加载，仓库不再只取第一页候选作为固定下拉 | 产品和仓库均使用动态搜索下拉，按编码或名称请求后端第一页，默认 `pageSize=10`，并缓存已选快照用于编辑回显 |
| 已改 | 库存余额 `/warehouse/stocks` | 筛选仓库选项不再取前 100 条或固定第一页后本地过滤 | 仓库筛选使用动态搜索下拉，按仓库编码或名称请求后端第一页，默认 `pageSize=10` |

统一处理方法：继续使用现有普通分页查询模型，不引入 cursor 或无限滚动，也不在下拉中展示 100 条长列表。简单对象选择器做成动态搜索下拉：使用组件库 `Popover + Command/Input + Button` 组合，用户输入编码或名称后短防抖请求第一页，默认 `pageSize=10`，弹层最多展示 10 条；无输入时显示搜索提示，或仅展示后端约定的最近/常用 10 条。复杂对象选择器做成分页选择弹窗：使用组件库 `Dialog`、`DialogScrollArea`、`Input`、`Button`、`Table`、`Pagination`，默认 `pageSize=20`，通过表格分页查看更多；产品、供货关系和订单引用优先使用这种形态。表单编辑已有记录时，已选中的供应商、客户、产品和仓库必须通过单据详情里的快照字段或按 ID 补查独立回显，不能依赖当前选项第一页。

## 4. 权限与登录态设计

系统权限库表设计中，MVP 阶段保留：

```text
sys_dept
sys_user
sys_role
sys_user_role
```

角色权限码直接保存在 `sys_role.permission_codes`，登录后由服务端把用户基础信息、角色编码和权限码放入 Redis session。前端不自行推导权限，只保存服务端返回的当前用户上下文。

请求鉴权采用 Sa-Token 原始 token。登录接口返回 `token` 和 `tokenName`，前端同时持久化两者，并在 Axios 请求拦截器中使用返回的 `tokenName` 作为请求头名称、`token` 作为请求头值；只有兼容旧登录数据时才回退为 `satoken`。应用刷新后通过 `/auth/me` 恢复并校验当前用户，接口返回 `401` 或退出登录时同时清理 token 与 tokenName。

## 5. 基础框架 + 登录模块

首个基础模块包含：

- 登录页 `/login`
- 后台主布局
- 工作台 `/dashboard`
- 路由守卫
- 当前用户状态
- 退出登录
- 404 页面

登录页默认在开发环境填入 `admin / 123456`，方便前端审核。后端接入后，可通过环境变量关闭 mock 登录并切换到真实接口。

后台主布局采用固定左侧菜单。MVP 阶段不设计 `sys_menu` 和动态路由表，权限由后端接口和页面进入后的权限码校验控制。后续如果拆出菜单权限表，可以把当前静态菜单迁移为后端菜单数据。

### 5.1 顶栏通知铃铛弹层

通知铃铛位于所有登录后页面的顶栏右侧、用户菜单左侧，用于快速回答“当前有什么需要我处理或关注”。当前阶段只建设轻量弹层，不新增独立消息中心页面，也不维护已读/未读历史。完整产品需求见 [PRD](product/PRD.md)。

弹层结构与交互：

- 铃铛徽标展示当前用户待处理业务事项数量，`0` 时隐藏，`1-99` 显示实际数量，超过 `99` 显示 `99+`。该数量不是未读数，打开弹层不会清零。
- 点击铃铛打开右对齐弹层，头部展示“待办与预警”、待处理数量和刷新状态；中部最多展示后端已排序的前 8 条待办；底部提供“进入工作台查看全部”。
- 每条待办展示业务标签、优先级、标题、聚合数量和最多两行影响说明，不在小弹层堆叠完整单据证据、错误堆栈或复杂指标。
- `completionMode=AUTO` 展示“去处理”并跳转 `route` 指定的采购、销售、仓储或库存页面；`completionMode=TRACKED` 展示“查看详情”并进入工作台异常详情；历史 `MANUAL` 只允许查看详情。铃铛内不直接审核、确认出入库或完成异常。
- 通知弹层与用户菜单互斥；点击外部、按 `Esc`、完成路由跳转或再次点击铃铛时关闭。弹层需要正确管理焦点和 `aria-label`。
- 首次进入主布局请求一次通知摘要。打开弹层或页面恢复前台时，若缓存超过 60 秒再刷新；缓存未过期时立即展示，不持续轮询。后台刷新保留旧数据，避免内容闪空。
- 空数据展示“当前没有待处理事项”；无缓存且请求失败时展示错误说明和“重新加载”；有缓存时继续展示旧数据并提示刷新失败。

数据与权限边界：

- 铃铛使用轻量 `GET /dashboard/notifications`，不得在全局主布局频繁请求包含趋势、排行和履约数据的 `/dashboard/overview`。
- 返回结构复用 `DashboardTodoItem`，后端负责权限裁剪、业务聚合、去重、总数和排序；前端不得自行并发查询各模块列表后拼装通知。
- 普通业务待办按采购、销售、仓储等模块权限返回；系统异常只返回给具备异常处理权限或被指派的用户、角色、部门，不能向普通员工广播。
- 弹层只展示 `PENDING` 事项。业务完成后由后端最新聚合结果自动减少数量或移除，不因为用户查看过就消失。
- 当前阶段不新增消息表、用户消息关系表或数据库字段；独立消息中心、已读状态、归档、搜索、批量操作、站外推送和实时连接均不在范围内。

字段契约：

| UI 标签 | API/schema 字段 | 类型 | 来源 | 可编辑 | 空值展示 | 备注 |
|---|---|---|---|---|---|---|
| 刷新时间 | `refreshedAt` | string | 后端生成 | 否 | `-` | 通知摘要生成时间 |
| 待处理数量 | `pendingCount` | integer | 后端按权限聚合 | 否 | `0` | 徽标最大显示 `99+`，不是未读数 |
| 高优先级数量 | `highPriorityCount` | integer | 后端按权限聚合 | 否 | `0` | 仅用于头部风险提示 |
| 是否还有更多 | `hasMore` | boolean | 后端计算 | 否 | `false` | 为真时引导进入工作台 |
| 待办列表 | `items[]` | object[] | 业务状态、风险和异常聚合 | 否 | 空列表 | 最多 8 条，复用 `DashboardTodoItem` |

### 5.2 工作台 `/dashboard`

工作台面向业务负责人、采购、销售和仓储人员，首屏用于快速判断“收入是否正常、订单是否阻塞、库存是否影响交付、哪些事项需要优先处理”。页面不做营销式大屏，也不要求前端并发拉取各业务列表再拼指标；统一使用 `/dashboard/overview` 获取后端已按当前用户权限裁剪的经营概览。

页面结构：

- 顶部四项摘要：今日销售额、本月毛利额、待处理订单、库存风险 SKU。
- 经营趋势：近 30 日销售额、采购额、毛利额折线图，前端在卡片内提供 7 天、15 天、30 天切换；切换后立即刷新数据视图，仅使用短时淡入/位移过渡，避免延迟重绘和明显卡顿；x 轴可见刻度数量必须随 7 天、15 天、30 天递增，刻度位置按绘图区等距分布，同时按间隔展示避免日期重叠。趋势图使用 5 条横向网格线、每个日期在线上以圆点标记，日期贴近图表底部，不在折线末端堆叠详细数值；图形区约占趋势卡片主体区域的 70%，下方保留数值明细表。趋势使用页面内轻量 SVG，复用现有 shadcn 卡片容器与全局 token，不再提供趋势详情弹窗。
- 业务待办：主卡展示优先级最高的前 8 条，包含采购单待审核、销售单待审核、待确认入库、待确认出库，以及后续接入的库存异常、库存扣减失败、外部同步异常、价格偏离、客户信用、AI 建议等需要人工审核、人工复核或人工修复的事项；点击待办项或“详情”在同页弹窗展示接口返回的全部待办。单据状态类待办只展示待处理数量和“处理对应业务后自动完成”，可通过“查看详情”展开接口返回的简要单据证据，再通过“前往完成”跳转对应业务页面；异常/人工修复类待办展示来源单号、错误信息、发生时间和“完成处理”，不提供无效的查看详情按钮，完成处理前必须弹出二次确认；价格偏离、客户信用等复核类待办展示产品/客户证据和关键指标。
- 订单流转：采购与销售单据在草稿、待审核、已审核、部分出入库、已完成阶段的数量；只在主卡展示，不提供详情弹窗。
- 销售商品排行：主卡展示近 30 日销售额前 5 名，并展示销量与可用库存，便于识别热销但低库存的商品；点击“查看详情”在弹窗展示接口返回的完整排行。
- 供应商履约：主卡展示核心供应商履约前 5 名，包含交付评分、质量评分和准时率；点击“查看详情”在弹窗展示完整排行。
- 库存预警：低可用库存 SKU、仓库、安全库存、建议补货数量、风险等级和最近出库时间；详情弹窗使用窄幅列表卡片展示完整预警数组，避免为少量字段制造不必要的横向滚动。

字段契约：

| UI 标签 | API/schema 字段 | 类型 | 来源 | 可编辑 | 空值展示 | 备注 |
|---|---|---|---|---|---|---|
| 刷新时间 | `refreshedAt` | string | 后端生成 | 否 | `-` | 工作台汇总数据生成时间 |
| 摘要指标 | `metrics[]` | object[] | 采购、销售、库存聚合 | 否 | 0 | 金额返回数值，前端格式化为人民币 |
| 经营趋势 | `trend[]` | object[] | 近 30 日销售、采购、毛利聚合 | 否 | 空图表 | 前端支持 7/15/30 天切换；毛利缺少真实成本时由后端统一说明估算口径 |
| 业务待办 | `todos[]` | object[] | 单据状态机、价格/信用复核、异常事件和人工任务聚合 | 否 | 空列表 | `businessType` 为可扩展事件源编码，`businessLabel` 为展示标签；`sortWeight` 由后端计算排序，`sourceMode` 区分动态聚合和持久化任务，`completionMode` 区分自动完成和手动完成；`evidence[]` 提供单据摘要、库存风险、价格/信用复核等查看详情依据 |
| 库存预警 | `stockAlerts[]` | object[] | `warehouse_stock` + 产品安全库存 | 否 | 空表格 | `availableQty = stockQty - lockedQty`，不同产品单位不混合汇总 |
| 订单流转 | `orderStages[]` | object[] | 采购/销售订单状态聚合 | 否 | 0 | 阶段名称用于展示，状态映射由后端统一维护 |
| 商品排行 | `topProducts[]` | object[] | 销售明细近 30 日聚合 | 否 | 空列表 | BIGINT ID 按字符串传输 |
| 供应商履约 | `supplierPerformance[]` | object[] | 供货关系和采购履约统计 | 否 | 空列表 | 评分为 0 到 100 数值 |

权限与口径：

- 工作台接口必须登录访问，后端按当前用户权限裁剪采购、销售、仓储等模块数据；无权模块返回 0 或空数组，不泄露业务数据。
- 工作台只展示经营概览、待办详情和人工完成入口，不在页面内执行审核、确认出入库、删除等业务写操作。
- 库存风险和待办数量应来自后端可执行查询、状态机统计或持久化待办任务，不由前端根据当前页列表推断全局业务状态。
- 待办处理建议采用“动态聚合 + 持久化异常任务”的混合模型：采购单待审核、销售单待审核、待确认入库、待确认出库、库存低于安全线等状态类待办使用 `sourceMode=AGGREGATED`、`completionMode=AUTO`，详情中默认不铺开大量单据号，只显示待处理数量、完成条件和“前往完成”入口；需要让业务人员判断是哪张单、什么问题时，可在 `evidence[]` 返回前 1-3 条代表性单据摘要，由前端点击“查看详情”展开，对应业务状态完成后在下一次 `/dashboard/overview` 中自动消失或数量变化；库存扣减失败、库存补偿失败、外部同步异常、AI 建议待确认等需要人工修复或人工复核的事件使用 `sourceMode=PERSISTED`、`completionMode=MANUAL`，建议后端新建待办任务表保存 `todoId`、事件源、来源单号、错误码、错误信息、处理建议、状态、处理人、处理时间和备注，再通过 `POST /dashboard/todos/{todoId}/complete` 完成处理；前端调用完成接口前必须展示确认弹窗，避免误点关闭异常。
- 待办可见范围和排序由后端负责：普通业务聚合待办按当前用户模块权限返回；异常/人工修复类待办只返回给具备处理权限、被指派用户、被指派角色或被指派部门范围内的人员，不发给普通员工。排序按 `sortWeight` 升序，其次按 `priority`、是否人工异常任务、发生时间倒序兜底；前端仅在后端临时未排序时做同样规则的兜底排序。
- 采购价偏离复核不是强制修改产品参考采购价，而是提示最近采购价高于产品参考采购价。详情必须展示产品编码/名称、供应商、来源采购单、参考采购价、最近采购价和偏离比例；业务人员先去采购订单确认报价是否合理，只有确认属于长期价格变化时才维护产品参考采购价。
- 客户信用待复核必须展示客户、来源销售单、授信额度、已占用额度、逾期天数等判断依据；业务人员前往客户或销售订单页面确认是否继续放行，不在工作台直接完成销售审核。
- 工作台不维护产品、仓库、客户、供应商下拉选项；需要选择或查看这些主数据时，跳转后的业务页面必须复用各模块已有分页查询接口和共享选择组件，例如产品分页、仓库分页、客户分页、供应商分页，不得在工作台接口一次性返回固定下拉列表。
- 前端仅负责类型校验、格式化展示和路由跳转；金额、数量、状态和风险等级进入页面前由 API 适配层做边界转换。
- `/dashboard/overview` 中 `todos`、`topProducts`、`supplierPerformance`、`stockAlerts` 返回工作台需要的完整明细数组；主页面只做摘要截取，详情弹窗展示同一数组，不再额外调用详情接口。
- 当前主页面截取规则：`todos` 展示前 8 条，`topProducts` 展示前 5 名，`supplierPerformance` 展示前 5 名；详情弹窗展示全部返回项。后端应按优先级、异常严重程度、影响金额、发生时间或履约综合表现排序后返回，避免前端二次猜测排序口径。
- 后端建议控制工作台数组规模：业务待办 20 条以内，销售商品排行 10 条以内，供应商履约 10 条以内，库存预警 20 条以内；超过建议数量时由后端按业务优先级截断并保持排序稳定。若后续人工修复类异常明显增多，应新增独立异常/任务中心分页接口，工作台只展示高优先级摘要和详情入口。

## 6. 模块生成与契约同步规则

每个模块的页面、接口和 Mock 必须与其数据库设计和 OpenAPI 契约保持一致。新增或修改页面时，同步更新：

```text
docs/api/erp-openapi.yaml
erp-web/src/modules/<模块>/types.ts
erp-web/src/modules/<模块>/api.ts
```

逐页的字段、筛选、状态和交互不再单独维护设计稿：字段来源以库表设计为准，接口形状以 OpenAPI 为准，视觉与交互以 [前端界面风格规范](frontend-style-guide.md) 为准，实际行为以 `erp-web/src/` 的正式实现为准。修改前先执行前端预检命令：

```powershell
cd erp-web
npm run preflight:frontend -- <scope>
```

模块页面生成顺序：

```text
1. 基础框架 + 登录模块
2. 系统权限模块
3. 产品模块
4. 仓库库存模块
5. 采购模块
6. 销售模块
7. AI 模块
```

每个模块完成后暂停，由用户审核页面代码和接口文档，再继续下一个模块。
