# 业务口径文档（注入给 AI 模型用）

这个目录里的每一份 Markdown 都会**按用户权限注入给 AI 模型**，作为它写取数要求的业务依据。

## 装配规则

```
权限码 → 模块前缀（取冒号前）→ knowledge/<模块>.md
```

| 权限码前缀 | 注入的文档 |
|---|---|
| `product` | `product.md` |
| `customer` | `customer.md` |
| `supplier` | `supplier.md` |
| `purchase` | `purchase.md` |
| `sales` | `sales.md` |
| `return` | `return.md` |
| `warehouse` | `warehouse.md` |
| `system` / `dashboard` / `ai` | 无对应文档（这三个模块没有业务表） |
| `*`（超管） | 全部 |

**`shared.md` 对所有用户都注入**——数量放大 100 倍、金额按分、状态名的中文读法、软删除规则、单号规则、日期语义，是读懂任何一张表的前提。

装配代码在 `AuthorizedKnowledgeProvider`，图节点是 `KnowledgeNode`。**装配失败会降级成空串继续跑**，不会让整轮规划挂掉。

## 写文档的规矩

1. **一条规则只写在一个文档里**，别的文档用「见 xxx.md」指过去。同一份口径注入两遍会白白吃掉模型的注意力。
2. **枚举值必须写英文字面量**（`APPROVED`、`PENDING_CONFIRM`），中文名只是给人看的。
3. **数字口径要写明**（×100 整数 / 分 / DECIMAL 不放大），模型据此写 `instruction`，并**给每个数字标单位**；换算只做一次，不在每个场景重复除 100。
4. **状态名的中文读法要单列**，因为枚举名直译经常是错的（`SUBMITTED` 是"待审核"不是"已提交"）。
5. **踩坑清单放最前面或最显眼的位置**——模型最容易犯的就是这些错。
6. **文档与代码不一致时以代码为准**，并在文档里标注出来，不要写代码里没有的断言（例：客户信用额度当前没有下单校验，就不能写成硬拦截）。
7. **业务定义要单独成节并给公式**：什么是滞销、周转天数、净缺口、延期交付，模型只能按这里定义的算，不能现场发明。知识里没有的口径，规划节点必须写明假设或请用户澄清。

## 统一章节结构（每份文档都按这个写）

```
# <模块>业务口径
> 适用范围：…
> 关联文档：…

## 一、速查（先看这几条）          ← 5~9 条最关键结论 + 最容易犯的错
## 二、对象与字段                  ← 表、粒度、字段口径、快照、引用关系
## 三、状态机与流转                ← 状态表、流转与校验、启停保护
## 四、关键口径                    ← 数量、金额、单位、时间归期、统计过滤
## 五、业务定义                    ← 本项目特有指标的定义与公式
## 六、常见错误                    ← 完整踩坑清单
## 七、写 instruction 时的提醒      ← 该写什么、必须标什么
```

- 编号和标题顺序固定，模型知道"定义去第五节找、坑去第六节找"。
- 某节确实没有内容就写「无」，不要跳号。
- 新增模块时按 `knowledge/_template.md` 复制。
- 写法风格参考 `proposal/common.md`：规则长在动作里，配具体反例，不写抽象禁止清单。

## 改完要做什么

```bash
cd erp-server
mvn -pl erp-ai -am test
```

`AuthorizedKnowledgeProviderTest` 会校验模块推导与注入顺序。改完文档不用重新发版——资源在 classpath 上，重启即生效。
