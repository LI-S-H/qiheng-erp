# 积压清仓规划

## 什么时候用

- 某些商品卖得慢、压着资金
- 继续放着还是降价、退供
- 积压的货能不能调给别的仓
- 清仓能清掉多少、还剩多少

判断库存整体健康、找出哪些商品可能滞销时，先用 `inventory-health`；已经确定要处置某批库存，再进入本技能。

## 系统边界

系统没有批次、库龄和到期日，也没有销货成本，因此：

- 不能报库龄、临期数量和确定可售量
- 不能算标准财务周转率，只能用出库速度推算覆盖天数
- 没有价格调整单据，降价只能改产品参考售价，没有审批和变更记录
- 库存流水没有调拨类型，调拨只能出建议，执行要另行确认

## 规划流程

### 第一步：确认是找候选还是做处置

| 用户怎么问 | 做什么 | 什么时候可以停 |
|---|---|---|
| 哪些商品卖得慢 | 给候选清单、筛选依据和数据限制 | 交清单即可，不急着给处置方案 |
| 这些货怎么处理 | 先确认候选，再做动作比较 | 给出各动作的数量、条件和缺口 |
| 继续放还是降价、退供 | 复用已有候选，直接比较动作 | 参数不足时给情景比较，不编最优解 |

### 第二步：确认范围和筛选口径

- 仓库、产品范围、观察窗口
- 慢销的判定阈值：多少天没有出库，或覆盖天数超过多少
- 阈值由用户给，没给就用"窗口内无出库"这种可验证的事实，不要默认 90 天

本技能只按用户给的阈值筛候选，不做库存健康诊断；要判断整体健康、找结构问题，调用 `inventory-health`。

### 第三步：确认可去化余量

当前库存不是可去化数量，要扣掉：

- 已锁定数量
- 保护期内确认的新增需求
- 期末要保留的缓冲

在途采购不能直接当额外库存，只有能在处置时点前到货的才算。

### 第四步：逐个比较动作

四种动作的必要条件不同，没选的不用全部取数：

| 动作 | 前提 | 不能承诺什么 |
|---|---|---|
| 暂停新增补货 | 是否还有在途或未审采购 | 不会直接减少现有库存 |
| 调拨 | 其他仓同一产品真的缺货 | 物流和到货时间未知时只列条件候选 |
| 降价 | 用户接受的价格或损失底线；要判断增利时转 `promotion` 测算 | 没有成本数据就不承诺增利 |
| 退供 | 有原采购来源、可退量、供应商同意 | 有退货流程不等于能退 |

### 第五步：交办分析专家

调用 `analyzeData`，不要自己用 `query_sql_data` 取明细。

- goal：写清产品范围、观察窗口、慢销阈值、处置目标、要比较的动作
- context：写明仓库、可去化余量的保留口径、用户给的价格或损失底线、供应商是否已同意退供
- 返回：候选清单和依据、可去化余量、各动作的可行数量与条件、未覆盖数量

### 第六步：解读

- 先交候选和判定依据，再说处置
- 每个动作给三件事：能做多少、需要什么条件、还差多少
- 四个动作共用同一个可去化上限，不能每个动作都按全量报
- 参数不足的动作给情景，不给唯一结论
- 说明系统限制：没有库龄、没有成本、降价无审批记录、调拨无单据

## 交付要求

- 候选清单列出编码、库存、未预占量、覆盖天数、最近出库日
- 判定口径写明用了什么窗口和阈值
- 可去化余量写清扣了哪些量
- 每个动作注明可行数量、前提条件和未覆盖数量
- 降价测算只给反推目标和情景，不编需求量
- 退供要有可退量和供应商态度，缺一项就不列为可执行

## 常见误判

- 把当前库存直接当可清数量
- 把覆盖天数说成库龄
- 用库存大推导出有人买
- 退供数量直接按库存报，忽略原采购来源和已退货占用
- 四个动作各自按全量报，合计超过可去化量
- 没有成本数据就得出降价一定增利的结论
- 把暂停补货算作已去化的数量

## 相关技能

- 先确认哪些商品积压：`inventory-health`
- 调拨到其他仓：`transfer`
- 降价测算和促销效果：`promotion`
- 清理后重新定补货规则：`inventory-policy`
