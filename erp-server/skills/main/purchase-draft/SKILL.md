# 采购草稿交付

## 什么时候用

- 采购方案已定，要生成采购单草稿给用户确认
- 用户确认、修改或驳回了草稿，需要继续推进
- 创建被系统拒绝，需要调整参数再来一次

缺口和采购量还没确定时，先走 `replenishment` 和 `purchase`，不要直接生成草稿。

## 第一步：确认草稿要素

生成前逐项确认，缺一项就先补齐或追问：

- 供应商：系统内真实存在且启用
- 入库仓库：系统内真实存在且启用
- 明细产品：属于该供应商的启用供货关系
- 数量：按起订量和精度取整后的可下单数量，不是缺口
- 单价：本次有效报价；没有则留空，由确认页按最新采购价回填
- 预计到货：有明确依据才填
- 备注：可填。只有用户明确要求记录说明时才填用户给出的内容，不要写 AI 的计算依据、来源或生成过程，没有就留空

供应商、仓库、产品的编号必须来自实际查询结果，不能编造或用名称代替。

## 第二步：调用工具

调用 `prepare_purchase_order_draft`，一次只提交一份草稿。

- 不需要提供金额合计，页面按明细自动计算
- 不需要提供供货关系编号，页面按供应商和产品解析
- 调用后本轮会停下等待用户处置，不要重复调用，也不要自己编造处置结果

等待期间用户的页面会显示草稿卡片，用户必须点开详情才能确认、编辑或驳回。

工具返回的是结论文字：第一句说明用户做了什么，后面按需附带参数 JSON。先读结论，需要精确数值时再读参数块，不要从文字里猜数字，也不要把参数块当成结论转述。

参数格式不合法时返回的是格式错误提示，按提示修正后重新调用，不会进入等待。

## 第三步：按处置结果继续

### created：用户直接确认

回执形如「用户接受了你的采购草稿参数，已生成单号为 PO2026112300001 的草稿单。」

- 给出采购单号，说明已创建为草稿
- 说明下一步：需要在采购单页面提交审核，审核通过后才进入待确认入库
- 不要描述成已经下单完成

### edited：用户修改后创建

回执会写明单号、最终参数 JSON、修改的字段和用户说明。先读用户说明和修改字段，再决定说什么：

- 用户说明是用户解释修改原因的原话，优先级最高；它说明了改动意图
- 修改的字段是发生变化的路径，例如 `items[0].quantity`、`warehouseId`
- 最终参数是用户确认的完整内容，后续分析都以此为准

回复顺序：

1. 用一句话复述用户的调整和意图，确认理解正确
2. 说明这次修改带来的好处：对缺口、库存、预算或交期的正向作用
3. 说明这次修改带来的弊端或代价：多占的资金、新增的风险、仍然没有解决的问题
4. 指出还有哪些部分没有覆盖
5. 给出下一步建议

好处和弊端都要有数据依据，需要时调用 `analyzeData` 进行数据分析，不能只凭变化方向推测幅度。

影响分析按变化类型选口径：

- 数量变化：库存覆盖天数和缺口日是否改善；多买占用的资金、少买可能再次缺货
- 单价变化：货值、预算占用、相对参考价的偏离；压价可能带来的交期或质量风险
- 仓库变化：目标仓缺口是否被覆盖、其他仓的调拨需求；跨仓调拨的运输成本
- 产品增删：新增产品是否有对应缺口、删除产品的缺口是否有其他来源；替代品的适配风险
- 到货日期变化：能不能赶上首次缺口日；提前到货带来的仓储占用

只改备注时：如果变化的字段只有 `remark` 或 `items[N].remark`，说明用户补充的是说明性内容，一句话确认即可，不做影响分析，也不要为了凑内容去查询数据。

只陈述事实和取舍，不评判用户的选择。用户既然改了，就按改后的方案继续。

### failed：系统拒绝了创建

回执形如「用户提交的采购草稿不符合系统生成规则：xxx。被拒参数：{...}」。先看第一句给出的原因，判断是哪一类：

- 参数问题：供应商停用、供货关系缺失、数量精度不符、单价越界、必填缺失
- 业务规则问题：价格低于参考价下限、重复单据、状态不允许

参数问题：修正对应字段后重新生成草稿，并说明改了什么。

业务规则问题：不能反复重试同一份参数。把规则原文告诉用户，给出满足规则的替代方案，等用户确认再生成。

被拒参数用于定位被拒绝的那一版内容。

### rejected：用户驳回了草稿

回执会写明驳回原因和补充要求：

- 驳回原因是用户勾选的一项或多项：价格过高、数量不合适、供应商不合适、交期太晚、收货仓不对、其他
- 补充要求是用户写下的具体约束，例如分批到货、指定品牌

按原因调整：

- 价格过高：换候选供应商或走议价，不要直接压价假设对方接受
- 数量不合适：重新核对缺口和起订量，说明为什么给出这个数量
- 供应商不合适：重新走 `supplier-selection`，不要沿用原评分结论
- 交期太晚：检查是否可以分批到货或改用其他仓库调拨
- 收货仓不对：重新确认目标仓和库存分布

调整后重新规划，可以再生成草稿，但不要在用户没有明确同意时反复提交。

## 交付要求

- 草稿参数必须能被系统直接校验通过，不提交明显会被拒的内容
- 说清楚草稿和正式采购单的区别：草稿创建后仍需提交审核
- 影响结论必须来自实际数据，不能凭变化方向推测幅度
- 用户驳回后先回应原因，再给方案，不要跳过原因直接生成新草稿

## 常见误判

- 把缺口数量直接写进草稿，忽略起订量和精度
- 用供应商名称或产品名称代替编号
- 用户修改后只复述数字变化，不解释影响
- 系统拒绝后不改参数就重复提交
- 用户驳回后不看原因，按原方案再生成一次
- 把 created 说成已经下单或已入库

## 相关技能

- 缺口计算：`replenishment`
- 采购量、货值、到货可行性：`purchase`
- 候选供应商和评分：`supplier-selection`
