# 采购单操作

## 动作一览

| 用户意图 | 调用工具 | 前置条件 |
|---|---|---|
| 生成新采购单 | `prepare_purchase_order_draft` | 缺口和采购量已确定 |
| 修改已有采购单 | `update_purchase_order_draft` | 采购单已经存在，且状态为草稿或待审核 |
| 提交审核 | `submit_purchase_order` | 用户同意提交，且单据是草稿 |
| 取消 | `cancel_purchase_order` | 用户同意取消，且未入库、未部分入库 |

## 动作之间的关系

- **创建 → 编辑**：只有创建成功、拿到采购单号之后才可能进入编辑。用户在创建前说要改什么，那是创建参数，走创建，不要调编辑。
- **创建/编辑 → 提交**：动作完成后主动问一句是否提交，用户同意才调提交。
- **取消**：可以主动建议（例如供应商交期赶不上、缺口已被其他来源覆盖），但必须先说明理由并询问用户，同意后才调。不要直接调，也不要反复劝。
- 状态不允许时不要硬调：待入库及之后不能编辑；已入库、部分入库不能取消；已取消不用再取消。
- 工具返回的是结论文本：第一句说明用户做了什么；修改后确认和系统拒绝会附最终参数或当前单据 JSON，先读结论，需要精确数值时再读参数块。

## 创建

调用 `prepare_purchase_order_draft`。

参数要求：

- 供应商、仓库、产品一律传数字主键 ID，不能传 S0001、WH000001、P001029 这类业务编码
- 用户只给编码时，先用 `query_sql_data` 按编码查出主键 ID，再生成草稿
- 供应商、仓库：真实存在且启用
- 明细产品：属于该供应商的启用供货关系
- 数量：按起订量和精度取整，不是缺口原值
- 单价：优先使用该供货关系的最新有效报价；模型参数可以省略，确认卡片会回填。仍没有有效报价时不要创建，提示用户补价或先维护供货关系，不能编造价格。
- 预计到货：补货场景按首次缺口日推算建议日期；无法推算才留空；填写时不得早于今天
- 备注：可填，只在用户明确要求记录说明时填写

回执处理：

- **用户确认创建**：给出单号，说明是草稿；然后问是否需要提交审核。
- **用户修改参数后创建**：先读用户说明和修改字段，复述调整意图，说明好处（缺口、库存、预算、交期）和弊端（多占资金、新增风险），数据依据调用 `analyzeData`；只改备注时只做一句确认。最后问是否需要提交审核。
- **用户驳回**：回应驳回原因，等用户给出新方向，不要按原参数再生成一次。
- **创建未通过**：判断是参数问题还是业务规则问题。参数问题修正后重新生成并说明改了什么；业务规则问题把规则原文告诉用户，给替代方案。

## 编辑

调用 `update_purchase_order_draft`，传 `purchaseOrderId` 和完整业务参数：`supplierId`、`warehouseId`、完整的 `items`，以及要改的日期、备注、单价。确认卡片只用单据详情做展示底稿，不能替你补工具参数。

- `purchaseOrderId` 必须是数字主键 ID，不能传采购单号
- 单据必须已经存在；不存在时不要调，先走创建
- 明细要传完整的 items，不要只传改动的那一行
- 如果上下文里没有当前单据的采购参数，先用 `query_sql_data` 查询单据详情或让用户提供；不要猜。确认卡片只做展示底稿，不替工具补必填参数
- 待审核状态编辑时，预计到货必须非空，且不得早于今天

回执处理：

- **用户确认修改**：说明已保存和当前状态；原来是草稿时问是否提交。
- **用户修改参数后保存**：同创建的修改处理，说明好处和弊端。
- **用户驳回**：采购单保持原样，回应原因即可。
- **修改未保存**：状态不允许就把当前状态告诉用户；参数问题给修复建议。

## 提交

调用 `submit_purchase_order`，只传 `purchaseOrderId`。

- 提交不产生新参数；预计到货为空时用户在卡片上补，不要编造
- 单据不是草稿时先说明状态，不要调用

回执处理：

- **用户同意提交**：说明当前是待审核，下一步等主管审核，不要说成已入库。
- **用户暂不提交**：按原因回应，不要反复询问。
- **提交未通过**：看错误原文。
  - 缺预计到货：提醒用户在卡片上补，或走编辑补日期
  - 供货关系失效、数量精度：给修复建议，用户确认后走编辑修改，保存后再问是否重新提交
  - 价格低于参考价下限、状态不允许：不能靠改参数绕过，给替代方案

## 取消

调用 `cancel_purchase_order`，传 `purchaseOrderId` 和从用户话里提取的 `reason`。

- 确认前提醒：取消是终态，不可恢复；待入库的采购单取消会同时作废未确认的入库单
- 只有草稿、待审核和未入库的已审核单据能取消

回执处理：

- **用户同意取消**：说明已取消和原因
- **用户暂不取消**：尊重决定，不再劝
- **取消失败**：按错误原文说明（例如已有入库事实不能取消），给下一步建议

## 查询采购单进度

用户问「我的采购单到哪一步了」「审核了吗」「为什么还没到货」时，用 `query_sql_data` 查状态和入库进度，再按状态机解释。

查询口径：

- 采购单：`purchase_order` 的 `status`、`expected_arrival_date`、`submitted_at`、`approved_at`
- 明细进度：`purchase_order_item` 的 `quantity`（订购量）和 `inbound_qty`（已入库量）
- 入库单：`inbound_bill` 中 `source_type = 'PURCHASE_ORDER'` 且 `source_id` 等于采购单 ID，看 `status` 和 `expected_arrival_date`

采购单状态：

| 状态 | 含义 | 下一步 |
|---|---|---|
| DRAFT | 草稿，尚未提交 | 需要提交审核 |
| SUBMITTED | 已提交，等主管审核 | 审核通过后才生成待确认入库单 |
| APPROVED | 已审核，已生成待确认入库单 | 等仓库确认入库 |
| PARTIAL_INBOUND | 部分入库 | 剩余数量仍在待入库 |
| INBOUND_DONE | 全部入库 | 流程结束，库存已更新 |
| CANCELLED | 已取消 | 终态，不会再到货 |

入库单状态：

| 状态 | 含义 |
|---|---|
| DRAFT | 草稿，尚未提交确认 |
| PENDING_CONFIRM | 待仓库确认 |
| CONFIRMED | 已确认，库存已更新 |
| CANCELLED | 已作废（采购单取消时联动） |

回答要求：

- 先说当前处于哪一步，再说卡在谁那里：等审核、等仓库确认、还是等供应商到货
- 部分入库要给出已入库和剩余数量，不要只说「部分入库」
- 预计到货日已过但仍是待入库时，说明可能是供应商延迟或仓库未确认，并告诉用户可以查什么确认
- 只回答查到的状态，不推测「应该快到了」这类结论
- 单据不存在或查不到时如实说明，不要编造进度

## 失败后的循环

提交或修改失败时：

1. 说明失败原因，给一句可执行的修复建议
2. 等用户确认或给出新参数
3. 同意后调用编辑工具修改
4. 保存成功后，问是否重新提交
5. 不要自动重试同一份参数，也不要在用户没有反馈时连续调用

## 交付要求

- 草稿参数必须能被系统直接校验通过，不提交明显会被拒的内容
- 说清楚草稿和正式采购单的区别：草稿创建后仍需提交审核
- 影响结论必须来自实际数据，不能凭变化方向推测幅度
- 用户驳回后先回应原因，再给方案

## 常见误判

- 把缺口数量直接写进草稿，忽略起订量和精度
- 用供应商名称或产品名称代替编号
- 用户修改后只复述数字变化，不解释影响
- 系统拒绝后不改参数就重复提交
- 用户驳回后不看原因，按原方案再生成一次
- 创建成功后没说还需要提交审核
- 用户没同意就调用提交或取消

## 相关技能

- 缺口计算：`replenishment`
- 采购量、货值、到货可行性：`purchase`
- 退回供应商的单据操作：`return-order`
- 候选供应商和评分：`supplier-selection`
