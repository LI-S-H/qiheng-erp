# 退货单操作

## 动作一览

| 用户意图 | 调用工具 | 前置条件 |
|---|---|---|
| 新建退货单 | `prepare_return_order_draft` | 退货方向、来源单、可退明细与数量已确认 |
| 修改已有退货单 | `update_return_order_draft` | 退货单已存在，状态为草稿或待审核 |
| 提交审核 | `submit_return_order` | 用户同意提交，且单据是草稿 |
| 取消 | `cancel_return_order` | 用户同意取消，且没有完成或部分执行 |

AI 不提供删除。用户要删除草稿时，提示到销售退货或采购退货页面操作。

## 先判断退货方向

退货单分两类，方向决定来源单类型、可退口径和执行方向，不能混：

| 方向 | returnType | 来源单 | 执行 |
|---|---|---|---|
| 客户把货退回来 | `SALES_RETURN` | 销售单，状态为部分出库或全部出库 | 审核后生成退货入库单 |
| 把货退回供应商 | `PURCHASE_RETURN` | 采购单，状态为部分入库或全部入库 | 审核后生成退货出库单 |

用户没说清是客户退货还是退供应商时，先问一句，不要猜。

## 可退数量口径

生成草稿前必须先查到可退上限，不能凭来源单的数量直接退。

- 销售退货：可退 = 来源明细已出库量 − 其他有效退货单占用
- 采购退货：可退 = min(来源明细已入库量 − 占用, 来源单仓库可用库存)
- 仓库可用库存 = `warehouse_stock.stock_qty − locked_qty`，只算来源单所在仓库
- 占用只算有效退货单：`DRAFT`、`CANCELLED` 不算；`SUBMITTED` 按申请量，`APPROVED` 及之后按审核量
- 同一来源单可以分多次退货，只要累计不超过上限

查询方式：调用 `query_returnable_items`，传 `returnType` 和来源单号，拿到每行的来源已履行量、已占用、仓库可用库存和最终可退量。工具不可用时，改用 `query_sql_data` 按上面的口径查询。

- 用户给了数量：先核对是否超过最终可退量，超了直接说明还能退多少，不要提交注定失败的数量
- 用户没给数量：按最终可退量给建议，并说明依据；不要编造
- 查不到来源单或所有行可退为 0：说明原因（未出库/未入库、已全部退过、仓库无库存），不要硬建

## 仓库规则

- 退货仓库必须等于来源单仓库，系统不允许换仓退货
- 用户要求从别的仓退时，说明只能按原单仓库退；如果原仓没有库存，需要先把货调拨回原仓

## 创建

调用 `prepare_return_order_draft`，一次一份。参数：

- `returnType`：必填，`SALES_RETURN` 或 `PURCHASE_RETURN`
- `sourceOrderId`：必填，来源单 ID
- `warehouseId`：必填，原单仓库
- `expectedExecutionDate`：可空，格式 yyyy-MM-dd；不能早于今天，提交前必须补
- `handlingType`：`REFUND`（退款/退回货款，默认）、`EXCHANGE`（换货）、`OTHER`（其他）；用户没有明确说换货或其他时用 `REFUND`
- `reasonCode`：7 个枚举之一
- `returnReason`：必填，写清退货事实；选 `OTHER` 时必须具体
- `remark`：可选
- `items`：`sourceOrderItemId`、`requestedQty`、`remark`；用来源明细 ID，不要用产品 ID；数量必须大于 0、符合产品精度、同一明细不能重复

退货原因码：

| 编码 | 含义 |
|---|---|
| `QUALITY_ISSUE` | 质量问题 |
| `DAMAGED` | 商品损坏 |
| `WRONG_ITEM` | 商品错发 |
| `QUANTITY_ERROR` | 数量错误 |
| `SPEC_MISMATCH` | 规格不符 |
| `NO_LONGER_NEEDED` | 不再需要 |
| `OTHER` | 其他原因 |

用户没有说明退货原因时先追问，不要套用默认原因或编造说明。

回执处理：

- **用户确认创建**：给出退货单号，说明是草稿、还没提交；然后问是否需要提交审核
- **用户修改参数后创建**：先读用户说明和修改字段，复述调整意图，说明影响（可退剩余、库存方向、执行安排）；只改备注时一句确认即可，最后问是否提交
- **用户驳回**：回应驳回原因，等用户给出新方向，不要按原参数再生成
- **创建未通过**：判断是参数问题还是业务规则问题。参数问题修正后重新生成；规则问题（超可退、换仓、来源单状态不符）把规则原文告诉用户，给替代方案

## 编辑

调用 `update_return_order_draft`，传 `returnOrderId` 和要改的字段。

- 只有草稿和待审核可以编辑
- 来源单和仓库不能改；明细要传完整的 items
- 不需要自己查当前单据，确认卡片会以单据详情为底
- 改数量时要重新核对可退上限，把其他退货单的占用算进去

回执处理与创建类似：确认保存、修改后保存、驳回、保存失败。

## 提交

调用 `submit_return_order`，只传 `returnOrderId`。

- 仅草稿可提交
- 预计执行日期必须已填写且不早于今天；为空时用户需要在卡片上补，不要编造
- 提交时后端会重新校验可退数量，其他退货单同时提交可能导致超量
- 提交后进入待审核，库存和执行单都还没变化

回执处理：

- **用户同意提交**：说明当前待审核，审核通过后才生成退货入库/出库单，不要说成已执行
- **用户暂不提交**：按原因回应，不要反复询问
- **提交未通过**：按错误原文说明。缺执行日期提醒补；可退不足给出当前上限；状态不符说明当前状态

## 取消

调用 `cancel_return_order`，传 `returnOrderId` 和从用户话里提取的 `reason`。

- 已部分执行、已完成、已取消的不能取消
- 草稿、待审核可以取消
- 已审核但没有任何执行事实的可以取消，取消时会作废未确认的退货入库/出库工作单
- 取消是终态，确认前要提醒

回执处理：同意取消说明结果和库存/工作单影响；暂不取消尊重决定；取消失败按错误原文说明。

## 查询退货单进度

用户问「退货单到哪一步了」「审核了吗」「为什么还没入库/出库」时，用 `query_sql_data` 查状态和执行进度，再按状态机解释。

查询口径：

- 退货单：`return_order` 的 `status`、`expected_execution_date`、`submitted_at`、`approved_at`
- 明细进度：`return_order_item` 的 `requested_qty`（申请量）和 `approved_qty`（审核量）
- 销售退货执行单：`inbound_bill` 中 `source_type = 'SALES_RETURN_ORDER'` 且 `source_id = return_order.id`
- 采购退货执行单：`outbound_bill` 中 `source_type = 'PURCHASE_RETURN_ORDER'` 且 `source_id = return_order.id`
- 执行单状态：`PENDING_CONFIRM` 待仓库确认、`CONFIRMED` 已确认、`CANCELLED` 已作废

退货单状态：

| 状态 | 含义 | 下一步 |
|---|---|---|
| DRAFT | 草稿，尚未提交 | 需要提交审核 |
| SUBMITTED | 已提交，等主管审核 | 审核通过后生成执行单 |
| APPROVED | 已审核，已生成执行单 | 销售退货等仓库确认入库；采购退货等仓库确认出库 |
| PARTIAL_EXECUTED | 部分执行 | 剩余数量仍在待执行 |
| COMPLETED | 全部执行 | 流程结束，库存与来源退回数量已更新 |
| CANCELLED | 已取消 | 终态，不会继续执行 |

回答要求：

- 先说当前状态，再说卡在谁那里：等审核、等仓库确认出库/入库
- 部分执行要给出已执行和剩余数量
- 预计执行日期已过但还没执行时，说明可能是仓库未确认，并告诉用户可以查什么
- 只回答查到的状态，不推测「应该快处理了」
- 单据不存在或查不到时如实说明，不要编造进度

## 失败后的循环

1. 说明失败原因，给一句可执行的修复建议
2. 等用户确认或给出新参数
3. 同意后调用编辑工具修改
4. 保存成功后，问是否重新提交
5. 不要自动重试同一份参数，也不要在用户没有反馈时连续调用

## 常见误判

- 用产品 ID 代替来源明细 ID
- 不看可退上限，直接按原单数量或估算数量建单
- 采购退货只看来源已入库量，忽略仓库可用库存
- 尝试换仓退货
- 把退货单当成修改原单，或建议用户直接改销售单/采购单代替退货
- 提交前没有补预计执行日期
- 把「已审核」说成「已入库/已出库」，忽略仓库确认环节
- 编造退货原因或原因说明
- 用户没同意就调用提交或取消

## 相关技能

- 退货原因分析、趋势、集中度：`returns`
- 原销售单的修改与状态：`sales-order`
- 原采购单的修改与状态：`purchase-order`
- 交付风险和库存影响：`fulfillment`、`inventory-health`
