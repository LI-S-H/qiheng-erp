# 退货分析规划

## 什么时候用

- 最近退货多不多、主要是哪类
- 退货原因是什么、集中在哪些产品
- 哪家供应商的退货明显偏多
- 客户退货是不是在变多、和什么有关
- 退货之后要不要重新采购、会不会影响供应

处理具体某批积压库存时用 `clearance`；评价供应商整体表现用 `supplier-selection`。

## 系统边界

- 系统只有退货单据，没有退货申请以外的处理流程；`handling_type` 目前只有退款
- 原因编码统一为 7 个枚举：`QUALITY_ISSUE`、`DAMAGED`、`WRONG_ITEM`、`QUANTITY_ERROR`、`SPEC_MISMATCH`、`NO_LONGER_NEEDED`、`OTHER`；历史旧码已迁移，不再存在 `QUALITY`、`CUSTOMER_RETURN`
- 退货单通过来源订单关联采购单或销售单，没有独立的产品成本信息
- 退货原因由人工填写，存在填写不一致的情况，按原因分组时要把样本量一起给出

## 规划流程

### 第一步：确认看哪类退货

| 用户问法 | 类型 | 关注点 |
|---|---|---|
| 供应商又退了多少 | 采购退货 | 退货率、供应商集中度、是否影响供货 |
| 客户退货变多了 | 销售退货 | 退货率、产品集中度、原因分布 |
| 退货为什么这么多 | 两类都看 | 原因分布和趋势 |
| 退货要不要补回来 | 采购退货 | 对库存和补货的影响 |

两类退货的分母完全不同，不要混在一起算一个总退货率。

### 第二步：确认范围和口径

- 哪些产品、供应商、客户、仓库
- 观察窗口：近 30 天、90 天、180 天，或按季度
- 按数量还是按金额
- 分母是采购入库量、销售出库量，还是订单量

不同口径结论可能相反，没确认先问。

### 第三步：确认问题类型

| 问题 | 需要的输出 |
|---|---|
| 退货多不多 | 退货率、与上期对比 |
| 为什么退 | 原因分布和主要产品 |
| 谁的问题 | 供应商或客户集中度 |
| 有没有影响 | 对库存、补货、供应的影响 |

### 第四步：交办分析专家

调用 `analyzeData`，不要自己用 `query_sql_data` 取明细。

- goal：写清退货类型、范围、窗口、口径和要回答的问题
- context：写明仓库、产品、供应商、观察窗口、分母口径
- 返回：退货量、退货率、原因分布、集中度、趋势、影响结论

### 第五步：解读

- 先给退货率和样本量，样本少时结论要打折
- 原因分布要区分"单次大批量"和"持续小批量"
- 供应商集中度高时，说明是偶发批次问题还是持续质量问题
- 退货影响库存时，说明是否影响后续补货和供应
- 原因编码存在人工填写差异，按原因下结论时说明这一点

## 交付要求

- 退货率和分母一起给，不只给一个百分比
- 原因分布列出前几项和各自占比
- 供应商或客户集中度给出金额或数量占比
- 趋势说明对比的基期
- 影响结论要区分已经发生的损失和潜在风险

## 常见误判

- 把采购退货和销售退货合成一个退货率
- 只用退货数量不看分母
- 把单次大批量退货当成持续质量问题
- 用小样本得出"某供应商质量差"的结论
- 把人工填写的原因编码当成准确分类
- 退货率高就直接建议换供应商，不区分原因

## 相关技能

- 单张退货单的创建、修改、提交、取消：`return-order`
- 评价供应商整体表现：`supplier-selection`
- 退货后的库存处置：`clearance`
- 退货影响供应时重新补货：`replenishment`
