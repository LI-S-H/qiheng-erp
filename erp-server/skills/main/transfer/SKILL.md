# 跨仓调拨规划

## 什么时候用

- 某个仓缺货，其他仓有库存
- 多个仓同时缺，先满足谁
- 调拨还是采购，哪个能接上缺口
- 源仓要留多少才不影响自己的需求

只算单仓补货量时调用 `replenishment`；缺口确认后要对外采购时调用 `purchase`；要改补货规则时调用 `inventory-policy`。

## 系统边界

系统目前没有调拨单据，库存流水类型只有采购入库、销售出库、采购退货、销售退货、调整入库、调整出库，没有调拨出入库。因此：

- 本技能只输出调拨建议：从哪个仓、调多少件、什么时间到、源仓留多少
- 如果执行时走调整出入库，库里留下的是调整记录，两仓的流水无法按同一笔业务对应，库存周转和出入库统计会受影响
- 给出建议时必须说明这一点，执行方式由用户决定

## 规划流程

### 第一步：确认对象和方向

- 产品必须相同，不能因为单位都叫"件"就互相替代
- 源仓、目标仓、建议数量或时间要求
- 是一次性调拨还是持续支援

### 第二步：确认源仓可释放量

账面库存不等于可调量，要扣掉：

- 已锁定数量：锁定已经包含未完成销售单的预占，不要再单独扣一次待出库需求
- 源仓保留量：安全库存，以及到下次到货前的预计需求

用户没有给保留策略时，按安全库存保留，并在答复里说明这是默认口径。

### 第三步：确认目标仓缺口

- 当前库存和锁定
- 在途采购及预计到货日
- 安全库存

缺口 = max(0, 保留量 − 净可用 − 缺口日前可到的在途)。待出库销售单的货已经在锁定里，不要重复扣，它只用来确定缺口发生在哪一天。已有在途能覆盖的部分要从缺口里扣掉。

### 第四步：确认时效

- 仓间运输时间系统里没有，需要用户提供，或按历史调拨记录估计
- 和采购交期比较：调拨通常更快，但要看实际运输和作业时间
- 到货日要能接上缺口发生日，接不上就说明调拨也解决不了

### 第五步：多目标仓分配

多个仓同时要货时，按顺序分配：

- 先满足缺口发生最早的仓
- 同一时点的缺口，按影响排序：有销售单待发、有合同或时效约束的优先
- 用户给了明确优先级就按用户口径，不要自己另定一套

分配算法见分析技能的参考文件。

### 第六步：交办分析专家

调用 `analyzeData`，不要自己用 `query_sql_data` 取明细。

- goal：写清产品、源仓、目标仓、数量或时间要求，以及要回答的问题
- context：写明候选仓、保留量口径、运输时间、用户给的优先级
- 返回：各仓净可用、可释放量、目标仓缺口、分配结果、调拨后余量、时效对比

### 第七步：解读

- 先说能不能调、最多能调多少
- 调拨后源仓是否仍不低于安全库存
- 调拨后目标仓能否撑到缺口日或下次到货
- 时效对比：调拨到货日与采购到货日分别是什么时候
- 说明系统没有调拨单据，执行后会留下什么记录

## 交付要求

- 可调量扣掉锁定和保留量，不能直接报账面库存
- 调拨数量按产品数量精度取整，不出现小数
- 到货时间注明来源：运输约定还是历史估计
- 目标仓缺口说明是否已经扣掉在途采购
- 多目标仓分配时说明分配依据和先后顺序

## 常见误判

- 把账面库存当可调量
- 调走源仓的安全库存，导致源仓转缺
- 忽略在途采购，重复计算缺口
- 只比成本不比到货时间
- 调拨量不取整，给出小数
- 说"调拨完成"，但系统里没有对应的调拨单据

## 相关技能

- 目标仓缺口怎么来的：`replenishment`
- 调拨接不上、需要对外采购：`purchase`
- 要不要长期靠调拨支援：`inventory-policy`
